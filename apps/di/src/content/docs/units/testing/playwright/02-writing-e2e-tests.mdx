Un test de Playwright describe lo que hace una persona: va a una página, encuentra un elemento, actúa sobre él y comprueba qué pasa. Las tres habilidades son **localizar** elementos de forma robusta, **actuar** sobre ellos y **afirmar** el resultado con aserciones que esperan por sí solas. Si vienes de Testing Library, reconocerás casi todo: los nombres son distintos, la filosofía es la misma.

<CardGrid stagger>
	<Card title="Locators" icon="magnifier">
		`page.getByRole`, `getByLabel`, `getByText`: describen el elemento como lo ve el usuario y se resuelven al usarlos.
	</Card>
	<Card title="Acciones" icon="approve-check">
		`click`, `fill`, `check`, `press`: esperan a que el elemento esté listo antes de actuar.
	</Card>
	<Card title="Aserciones" icon="seti:clock">
		`await expect(locator).toBeVisible()`: reintenta hasta cumplirse o agotar el tiempo. Sin esperas manuales.
	</Card>

## Anatomía de un test

```ts title="tests/tasks.spec.ts"
import { test, expect } from "@playwright/test";

test("adding a task shows it in the list", async ({ page }) => {
	await page.goto("http://localhost:5173/");

	await page.getByLabel("New task").fill("Learn Playwright");
	await page.getByRole("button", { name: "Add" }).click();

	await expect(page.getByRole("listitem")).toHaveCount(1);
	await expect(page.getByText("Learn Playwright")).toBeVisible();
});
```

<Steps>
	1. **`test(nombre, fn)`** define un test. La función recibe **fixtures**; `page` es una pestaña nueva y limpia para este test.
	2. **`page.goto(url)`** navega. Con `baseURL` configurada (siguiente página) basta `page.goto("/")`.
	3. **Locator + acción**: `getByLabel("New task")` describe el campo; `.fill()` escribe en él. El locator **no busca nada** hasta que se usa.
	4. **`await expect(locator).matcher()`**: la aserción espera a que se cumpla. El `await` delante de `expect` es obligatorio.
</Steps>

Todo lleva `await` porque cada paso es una orden al navegador que tarda en completarse. Olvidar uno hace que el test continúe antes de tiempo y falle de forma confusa.

## Locators: encontrar elementos

Un *locator* es una **descripción** de cómo encontrar uno o varios elementos. Playwright lo resuelve en el momento de actuar, y vuelve a resolverlo en cada reintento; por eso los tests no se rompen porque la página tarde en pintar.

| Locator | Encuentra por | Ejemplo |
| :--- | :--- | :--- |
| `getByRole` | rol accesible y nombre | `page.getByRole("button", { name: "Add" })` |
| `getByLabel` | la etiqueta de un campo | `page.getByLabel("New task")` |
| `getByPlaceholder` | el placeholder | `page.getByPlaceholder("What needs to be done?")` |
| `getByText` | el texto visible | `page.getByText("No tasks")` |
| `getByTitle` | el atributo `title` | `page.getByTitle("Close")` |
| `getByTestId` | `data-testid` | `page.getByTestId("total")` |
| `locator(css)` | selector CSS o XPath | `page.locator("ul > li")` (último recurso) |

El orden es el mismo que en Testing Library: primero rol, luego etiqueta y texto, y `locator("css")` solo cuando no hay alternativa, porque se rompe al cambiar el HTML.

### Afinar un locator

```ts
// exact text (default is "contains", case-insensitive)
page.getByText("Tasks", { exact: true });

// chaining: an element inside another
page.getByRole("listitem").filter({ hasText: "Commit changes" }).getByRole("checkbox");

// by position, when several match
page.getByRole("listitem").first();
page.getByRole("listitem").nth(2);
page.getByRole("listitem").last();
```

`filter({ hasText })` es la forma habitual de llegar a "el botón de eliminar **de esta** fila": localizas la fila por su texto y, dentro, el botón.

<Aside type="caution" title="Un locator que coincide con varios elementos">
	Si haces `click()` sobre un locator que resuelve a dos elementos, Playwright falla con *strict mode violation* en lugar de elegir uno al azar. Es deliberado: afina con `filter`, `first()` o un nombre más concreto.
</Aside>

## Acciones

| Acción | Qué hace | Espera antes a que… |
| :--- | :--- | :--- |
| `click()` | clic | sea visible, estable y reciba eventos |
| `fill(texto)` | borra y escribe | sea editable |
| `press("Enter")` | pulsa una tecla | tenga foco |
| `check()` / `uncheck()` | marca un checkbox | sea visible y habilitado |
| `selectOption("valor")` | elige en un `<select>` | |
| `hover()` | pasa el ratón | |
| `setInputFiles(ruta)` | sube un archivo | |

```ts
await page.getByLabel("New task").fill("Buy bread");
await page.getByLabel("New task").press("Enter");
await page.getByRole("checkbox", { name: "Buy bread" }).check();
await page.getByRole("button", { name: "Completed" }).click();
```

La espera automática (*auto-wait*) es lo que hace a Playwright fiable: no necesitas comprobar que el botón existe antes de pulsarlo. Si no llega a estar listo en el tiempo límite (30 s por defecto), el test falla con un mensaje que explica qué condición no se cumplió.

## Aserciones

Hay dos familias. Las de **locator** reintentan hasta cumplirse; las genéricas (las de Vitest) comprueban un valor una sola vez.

<Tabs>
	<TabItem label="Sobre locators (reintentan)">
		```ts
		await expect(page.getByText("0 pending")).toBeVisible();
		await expect(page.getByRole("listitem")).toHaveCount(2);
		await expect(page.getByRole("checkbox", { name: "Done" })).toBeChecked();
		await expect(page.getByRole("button", { name: "Add" })).toBeDisabled();
		await expect(page.getByLabel("New task")).toHaveValue("");
		await expect(page.getByRole("heading")).toHaveText("Tasks");
		await expect(page.getByText("Error")).not.toBeVisible();
		await expect(page.getByText("Temporary")).toBeHidden();
		```
	</TabItem>
	<TabItem label="Sobre la página">
		```ts
		await expect(page).toHaveTitle(/Tasks/);
		await expect(page).toHaveURL(/\/tasks/);
		```
	</TabItem>
	<TabItem label="Genéricas (sin reintento)">
		```ts
		const total = await page.getByRole("listitem").count();
		expect(total).toBe(2);   // checks once; fails if the list has not rendered yet
		```

		Úsalas solo con valores que ya has extraído. Para el DOM, siempre las de locator.
	</TabItem>
</Tabs>

<Aside type="tip" title="Por qué `toHaveCount` y no `count()`">
	`await expect(locator).toHaveCount(2)` espera hasta que haya exactamente dos; `expect(await locator.count()).toBe(2)` cuenta **ahora** y, si la app todavía está renderizando, falla aunque un instante después hubiera dos. Casi todos los tests "intermitentes" vienen de usar la segunda forma.
</Aside>

## Organizar: `beforeEach` y `describe`

```ts title="tests/tasks.spec.ts"
import { test, expect } from "@playwright/test";

test.beforeEach(async ({ page }) => {
	await page.goto("/");
});

test.describe("task management", () => {
	test("starts empty", async ({ page }) => {
		await expect(page.getByText("No tasks")).toBeVisible();
		await expect(page.getByText("0 pending")).toBeVisible();
	});

	test("adding a task shows it in the list", async ({ page }) => {
		await page.getByLabel("New task").fill("Learn Playwright");
		await page.getByRole("button", { name: "Add" }).click();

		await expect(page.getByRole("listitem")).toHaveCount(1);
		await expect(page.getByText("1 pending")).toBeVisible();
	});

	test("completing a task updates the counter", async ({ page }) => {
		await page.getByLabel("New task").fill("Learn Playwright");
		await page.getByRole("button", { name: "Add" }).click();
		await page.getByRole("checkbox", { name: "Learn Playwright" }).check();

		await expect(page.getByText("0 pending")).toBeVisible();
	});
});
```

`test.beforeEach` se ejecuta antes de cada test con su propia `page` nueva. Como cada test parte de un navegador limpio, no hay estado compartido: el tercero no ve la tarea que añadió el segundo. Eso es lo que permite ejecutarlos en paralelo y en cualquier orden.

### Reducir repetición

Igual que en Vitest, una función auxiliar evita copiar los pasos comunes:

```ts
async function addTask(page: Page, title: string) {
	await page.getByLabel("New task").fill(title);
	await page.getByRole("button", { name: "Add" }).click();
}
```

Importa el tipo con `import { test, expect, type Page } from "@playwright/test";`. Para flujos más largos (login, crear datos de partida) Playwright ofrece *fixtures* personalizadas; para este módulo, las funciones auxiliares bastan.

## Qué probar en un E2E

<Tabs>
	<TabItem label="Sí">
		- El **camino feliz** de cada flujo principal: crear, ver, modificar, borrar.
		- Lo que **cruza** varias pantallas o componentes: añadir y luego filtrar; hacer login y llegar al panel.
		- Lo que depende del **navegador**: navegación, URL, título, foco, que el botón no esté tapado.
		- Un caso de **error visible** por flujo: enviar vacío, credenciales incorrectas.
	</TabItem>
	<TabItem label="No">
		- Cada combinación de datos de una función: eso es un test unitario con `it.each`.
		- Estados internos o props: no existen desde el navegador.
		- Detalles de estilo (colores, márgenes): si importan, capturas visuales; si no, nada.
		- Lo que ya cubre un test de integración más barato.
	</TabItem>
</Tabs>

## 🧩 Aplicación en el proyecto

En tu aplicación React, la lista de tests E2E suele caber en una mano:

- **Carga inicial**: la página abre, el título es el correcto, el estado vacío se muestra.
- **Flujo principal completo**: crear un elemento, verlo en la lista, editarlo o completarlo, eliminarlo.
- **Filtros o navegación**: cambiar de vista y comprobar qué se muestra y qué no.
- **Un error visible**: enviar un formulario inválido y ver el mensaje.

Cuatro o cinco tests que, si pasan, garantizan que la app es usable. Todo lo demás, en Vitest.

## Resumen rápido

| Paso | API |
| :--- | :--- |
| Navegar | `await page.goto("/")` |
| Localizar | `page.getByRole("button", { name })`, `getByLabel`, `getByText`, `getByPlaceholder` |
| Afinar | `{ exact: true }`, `.filter({ hasText })`, `.first()`, `.nth(i)` |
| Actuar | `.click()`, `.fill()`, `.press("Enter")`, `.check()`, `.selectOption()` |
| Afirmar | `await expect(loc).toBeVisible() / toHaveCount(n) / toHaveText() / toBeChecked() / toBeDisabled()` |
| Página | `await expect(page).toHaveTitle() / toHaveURL()` |
| Organizar | `test.beforeEach`, `test.describe`, funciones auxiliares |

## Convención práctica

<Steps>
	1. **`await` en todo**: acciones, navegaciones y aserciones sobre locators.
	2. Localiza por **rol y nombre**; `locator("css")` solo si no hay otra opción, y documenta por qué.
	3. Aserciones **sobre locators**, no sobre valores extraídos con `count()` o `textContent()`.
	4. Un test, **un flujo**; `beforeEach` para la navegación inicial común.
	5. Si el test necesita datos previos (una tarea ya creada), créalos **por la interfaz** o por la API, nunca manipulando el estado de la app.
</Steps>
