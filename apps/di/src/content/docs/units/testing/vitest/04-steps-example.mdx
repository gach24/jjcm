## Paso 1 — Crea el proyecto e instala las herramientas

El proyecto base es el de [Preparar el proyecto](/jjcm/di/units/testing/vitest/00-project-setup/): una app React con Vite llamada `task-app`, limpia de ejemplos y con `src/App.tsx` devolviendo `<main />`. Si no lo tienes, créalo siguiendo esa página y vuelve aquí.

Con el servidor de desarrollo parado (`Ctrl+C`), dentro de `task-app`, instala Vitest y Testing Library como dependencias de desarrollo:

```bash
npm install -D vitest jsdom @testing-library/react @testing-library/dom @testing-library/user-event @testing-library/jest-dom
```

Al terminar aparecen en el bloque `devDependencies` de `package.json`.

Sustituye el contenido de `vite.config.ts` y crea el archivo de setup:

```ts title="vite.config.ts"

import react from "@vitejs/plugin-react";

export default defineConfig({
	plugins: [react()],
	test: {
		environment: "jsdom",
		setupFiles: "./src/setupTests.ts",
	},
});
```

```ts title="src/setupTests.ts"
import "@testing-library/jest-dom/vitest";

```

Y el script de test en `package.json`:

## Paso 2 — La lógica pura y sus tests

Toda la lógica de la app está en funciones **puras**: reciben la lista de tareas y devuelven una nueva, sin modificar la original. Son las más fáciles de probar y las que más conviene tener cubiertas.

```ts title="src/utils/tasks.ts"
export interface Task {
	id: number;
	title: string;
	done: boolean;
}

export type Filter = "all" | "active" | "done";

export function addTask(tasks: Task[], title: string): Task[] {
	const clean = title.trim();
	if (clean === "") return tasks;
	const id = tasks.length === 0 ? 1 : Math.max(...tasks.map(t => t.id)) + 1;
	return [...tasks, { id, title: clean, done: false }];
}

export function toggleTask(tasks: Task[], id: number): Task[] {
	return tasks.map(t => (t.id === id ? { ...t, done: !t.done } : t));
}

export function removeTask(tasks: Task[], id: number): Task[] {
	return tasks.filter(t => t.id !== id);
}

export function filterTasks(tasks: Task[], filter: Filter): Task[] {
	if (filter === "active") return tasks.filter(t => !t.done);
	if (filter === "done") return tasks.filter(t => t.done);
	return tasks;
}

export function countActive(tasks: Task[]): number {
	return tasks.filter(t => !t.done).length;
}
```

```ts title="src/utils/tasks.test.ts"
import { describe, it, expect } from "vitest";
import { addTask, toggleTask, removeTask, filterTasks, countActive, type Task } from "./tasks";

const base: Task[] = [
	{ id: 1, title: "Learn Vitest", done: false },
	{ id: 2, title: "Commit changes", done: true },
];

describe("addTask", () => {
	it("appends a task with a new id", () => {
		const result = addTask(base, "New");
		expect(result).toHaveLength(3);
		expect(result[2]).toEqual({ id: 3, title: "New", done: false });
	});

	it("trims the title", () => {
		expect(addTask([], "  Hello  ")[0].title).toBe("Hello");
	});

	it("ignores empty titles", () => {
		expect(addTask(base, "   ")).toBe(base);
	});

	it("does not mutate the original list", () => {
		addTask(base, "Another");
		expect(base).toHaveLength(2);
	});
});

describe("toggleTask", () => {
	it("toggles the given task", () => {
		const result = toggleTask(base, 1);
		expect(result[0].done).toBe(true);
		expect(result[1].done).toBe(true);
	});

	it("leaves the other tasks untouched", () => {
		const result = toggleTask(base, 2);
		expect(result[0]).toEqual(base[0]);
	});
});

describe("removeTask", () => {
	it("removes the task by id", () => {
		expect(removeTask(base, 1)).toEqual([base[1]]);
	});

	it("returns the same list when the id does not exist", () => {
		expect(removeTask(base, 99)).toEqual(base);
	});
});

describe("filterTasks", () => {
	it.each([
		["all", 2],
		["active", 1],
		["done", 1],
	] as const)("with filter %s returns %i tasks", (filter, expected) => {
		expect(filterTasks(base, filter)).toHaveLength(expected);
	});
});

describe("countActive", () => {
	it("counts the pending tasks", () => {
		expect(countActive(base)).toBe(1);
	});

	it("returns 0 for an empty list", () => {
		expect(countActive([])).toBe(0);
	});
});
```

Ejecuta `npm test`: deben pasar 13 tests. Fíjate en los casos cubiertos de cada función: el normal, el límite (lista vacía, id inexistente) y la inmutabilidad.

## Paso 3 — Los componentes y sus tests

### 3.1 — `TaskForm`

Un campo y un botón. El botón se deshabilita mientras el campo está vacío; al enviar, avisa por `onAdd` y se limpia.

```tsx title="src/components/TaskForm.tsx"
import { useState, type FormEvent } from "react";

interface Props {
	onAdd: (title: string) => void;
}

export function TaskForm({ onAdd }: Props) {
	const [title, setTitle] = useState("");

	function handleSubmit(e: FormEvent) {
		e.preventDefault();
		onAdd(title);
		setTitle("");
	}

	return (
		<form onSubmit={handleSubmit}>
			<label htmlFor="new-task">New task</label>
			<input
				id="new-task"
				value={title}
				onChange={e => setTitle(e.target.value)}
				placeholder="What needs to be done?"
			/>
			<button type="submit" disabled={title.trim() === ""}>
				Add
			</button>
		</form>
	);
}
```

```tsx title="src/components/TaskForm.test.tsx"
import { describe, it, expect, vi } from "vitest";
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { TaskForm } from "./TaskForm";

describe("TaskForm", () => {
	it("disables the button when the field is empty", () => {
		render(<TaskForm onAdd={() => {}} />);
		expect(screen.getByRole("button", { name: "Add" })).toBeDisabled();
	});

	it("enables the button when typing", async () => {
		const user = userEvent.setup();
		render(<TaskForm onAdd={() => {}} />);

		await user.type(screen.getByLabelText("New task"), "Something");

		expect(screen.getByRole("button", { name: "Add" })).toBeEnabled();
	});

	it("calls onAdd with the title and clears the field", async () => {
		const user = userEvent.setup();
		const onAdd = vi.fn();
		render(<TaskForm onAdd={onAdd} />);

		const input = screen.getByLabelText("New task");
		await user.type(input, "Learn Vitest");
		await user.click(screen.getByRole("button", { name: "Add" }));

		expect(onAdd).toHaveBeenCalledWith("Learn Vitest");
		expect(input).toHaveValue("");
	});

	it("also submits with Enter", async () => {
		const user = userEvent.setup();
		const onAdd = vi.fn();
		render(<TaskForm onAdd={onAdd} />);

		await user.type(screen.getByLabelText("New task"), "With Enter{Enter}");

		expect(onAdd).toHaveBeenCalledWith("With Enter");
	});
});
```

### 3.2 — `TaskList`

Recibe las tareas y dos callbacks. Cada tarea es un checkbox con su título y un botón de eliminar. Sin tareas, muestra un mensaje.

```tsx title="src/components/TaskList.tsx"
import type { Task } from "../utils/tasks";

interface Props {
	tasks: Task[];
	onToggle: (id: number) => void;
	onRemove: (id: number) => void;
}

export function TaskList({ tasks, onToggle, onRemove }: Props) {
	if (tasks.length === 0) {
		return <p>No tasks</p>;
	}

	return (
		<ul>
			{tasks.map(task => (
				<li key={task.id}>
					<label>
						<input type="checkbox" checked={task.done} onChange={() => onToggle(task.id)} />
						<span style={{ textDecoration: task.done ? "line-through" : "none" }}>{task.title}</span>
					</label>
					<button onClick={() => onRemove(task.id)} aria-label={`Delete ${task.title}`}>
						×
					</button>
				</li>
			))}
		</ul>
	);
}
```

```tsx title="src/components/TaskList.test.tsx"
import { describe, it, expect, vi } from "vitest";
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { TaskList } from "./TaskList";
import type { Task } from "../utils/tasks";

const tasks: Task[] = [
	{ id: 1, title: "Learn Vitest", done: false },
	{ id: 2, title: "Commit changes", done: true },
];

describe("TaskList", () => {
	it("shows a message when there are no tasks", () => {
		render(<TaskList tasks={[]} onToggle={() => {}} onRemove={() => {}} />);
		expect(screen.getByText("No tasks")).toBeInTheDocument();
		expect(screen.queryByRole("list")).not.toBeInTheDocument();
	});

	it("renders one row per task with its state", () => {
		render(<TaskList tasks={tasks} onToggle={() => {}} onRemove={() => {}} />);

		expect(screen.getAllByRole("listitem")).toHaveLength(2);
		expect(screen.getByRole("checkbox", { name: "Learn Vitest" })).not.toBeChecked();
		expect(screen.getByRole("checkbox", { name: "Commit changes" })).toBeChecked();
	});

	it("calls onToggle with the id when checking", async () => {
		const user = userEvent.setup();
		const onToggle = vi.fn();
		render(<TaskList tasks={tasks} onToggle={onToggle} onRemove={() => {}} />);

		await user.click(screen.getByRole("checkbox", { name: "Learn Vitest" }));

		expect(onToggle).toHaveBeenCalledWith(1);
	});

	it("calls onRemove with the id when deleting", async () => {
		const user = userEvent.setup();
		const onRemove = vi.fn();
		render(<TaskList tasks={tasks} onToggle={() => {}} onRemove={onRemove} />);

		await user.click(screen.getByRole("button", { name: "Delete Commit changes" }));

		expect(onRemove).toHaveBeenCalledWith(2);
	});
});
```

<Aside type="note" title="Por qué `aria-label` en el botón ×">
	Un botón cuyo texto es "×" no tiene un nombre accesible útil: ni un lector de pantalla ni el test sabrían qué elimina. `aria-label="Delete Commit changes"` le da nombre, y ese nombre es lo que usa `getByRole`. Escribir tests con Testing Library mejora la accesibilidad casi sin querer.
</Aside>

### 3.3 — `TaskFilter`

Tres botones; el activo lleva `aria-pressed="true"`.

```tsx title="src/components/TaskFilter.tsx"
import type { Filter } from "../utils/tasks";

interface Props {
	value: Filter;
	onChange: (filter: Filter) => void;
}

const options: { value: Filter; label: string }[] = [
	{ value: "all", label: "All" },
	{ value: "active", label: "Active" },
	{ value: "done", label: "Completed" },
];

export function TaskFilter({ value, onChange }: Props) {
	return (
		<div role="group" aria-label="Filter">
			{options.map(option => (
				<button
					key={option.value}
					onClick={() => onChange(option.value)}
					aria-pressed={value === option.value}
				>
					{option.label}
				</button>
			))}
		</div>
	);
}
```

```tsx title="src/components/TaskFilter.test.tsx"
import { describe, it, expect, vi } from "vitest";
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { TaskFilter } from "./TaskFilter";

describe("TaskFilter", () => {
	it("marks the active filter as pressed", () => {
		render(<TaskFilter value="active" onChange={() => {}} />);

		expect(screen.getByRole("button", { name: "Active" })).toHaveAttribute("aria-pressed", "true");
		expect(screen.getByRole("button", { name: "All" })).toHaveAttribute("aria-pressed", "false");
	});

	it("calls onChange with the chosen filter", async () => {
		const user = userEvent.setup();
		const onChange = vi.fn();
		render(<TaskFilter value="all" onChange={onChange} />);

		await user.click(screen.getByRole("button", { name: "Completed" }));

		expect(onChange).toHaveBeenCalledWith("done");
	});
});
```

## Paso 4 — La aplicación completa

`App` guarda el estado y conecta las piezas. No tiene lógica propia: delega en las funciones de `utils/tasks.ts`.

```tsx title="src/App.tsx"
import { useState } from "react";
import { TaskForm } from "./components/TaskForm";
import { TaskList } from "./components/TaskList";
import { TaskFilter } from "./components/TaskFilter";
import {
	addTask,
	toggleTask,
	removeTask,
	filterTasks,
	countActive,
	type Task,
	type Filter,
} from "./utils/tasks";

export default function App() {
	const [tasks, setTasks] = useState<Task[]>([]);
	const [filter, setFilter] = useState<Filter>("all");

	return (
		<main>
			<h1>Tasks</h1>
			<TaskForm onAdd={title => setTasks(addTask(tasks, title))} />
			<TaskFilter value={filter} onChange={setFilter} />
			<TaskList
				tasks={filterTasks(tasks, filter)}
				onToggle={id => setTasks(toggleTask(tasks, id))}
				onRemove={id => setTasks(removeTask(tasks, id))}
			/>
			<p>{countActive(tasks)} pending</p>
		</main>
	);
}
```

Arranca `npm run dev` y comprueba a mano que funciona. Después, el test de **integración**: usa los componentes reales juntos, sin mocks, y recorre un flujo completo como lo haría el usuario.

```tsx title="src/App.test.tsx"
import { describe, it, expect } from "vitest";
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import App from "./App";

async function addTask(user: ReturnType<typeof userEvent.setup>, title: string) {
	await user.type(screen.getByLabelText("New task"), title);
	await user.click(screen.getByRole("button", { name: "Add" }));
}

describe("App", () => {
	it("starts without tasks", () => {
		render(<App />);
		expect(screen.getByText("No tasks")).toBeInTheDocument();
		expect(screen.getByText("0 pending")).toBeInTheDocument();
	});

	it("adds tasks and updates the counter", async () => {
		const user = userEvent.setup();
		render(<App />);

		await addTask(user, "Learn Vitest");
		await addTask(user, "Commit changes");

		expect(screen.getAllByRole("listitem")).toHaveLength(2);
		expect(screen.getByText("2 pending")).toBeInTheDocument();
	});

	it("completing a task decrements the counter", async () => {
		const user = userEvent.setup();
		render(<App />);

		await addTask(user, "Learn Vitest");
		await user.click(screen.getByRole("checkbox", { name: "Learn Vitest" }));

		expect(screen.getByText("0 pending")).toBeInTheDocument();
	});

	it("the Completed filter hides pending tasks", async () => {
		const user = userEvent.setup();
		render(<App />);

		await addTask(user, "Pending");
		await addTask(user, "Done");
		await user.click(screen.getByRole("checkbox", { name: "Done" }));
		await user.click(screen.getByRole("button", { name: "Completed" }));

		expect(screen.getByRole("checkbox", { name: "Done" })).toBeInTheDocument();
		expect(screen.queryByRole("checkbox", { name: "Pending" })).not.toBeInTheDocument();
	});

	it("deleting a task removes it from the list", async () => {
		const user = userEvent.setup();
		render(<App />);

		await addTask(user, "Temporary");
		await user.click(screen.getByRole("button", { name: "Delete Temporary" }));

		expect(screen.getByText("No tasks")).toBeInTheDocument();
	});
});
```

La función auxiliar `addTask` del test evita repetir las dos líneas de añadir en cada caso. Es habitual tener pequeñas ayudas así dentro del archivo de test.

### Qué deberías observar

- Los tests de **utilidades** son instantáneos; los de **componentes** tardan algo más (montan un DOM). Aun así, todo el conjunto corre en un par de segundos.
- Si rompes `countActive` (por ejemplo, contando las hechas), fallan **dos niveles**: su test unitario y el de integración de `App`. El unitario te dice *dónde*; el de integración, *qué nota el usuario*.
- Si cambias el texto del botón "Add" por "Agregar", fallan los tests que lo buscan por nombre. Es correcto: ese texto es parte del comportamiento visible.

### Cobertura

```bash
npm install -D @vitest/coverage-v8
npx vitest run --coverage
```

Muestra el porcentaje de líneas, ramas y funciones ejecutadas por los tests, archivo por archivo. En esta app debería acercarse al 100 % en `utils/` y `components/`. No persigas el 100 % en general; úsalo para **descubrir** ramas sin probar (un `if` cuyo `else` nunca se ejecuta).

## Paso 6 — Ejecutar en GitHub Actions

Para que los tests corran en cada `push` y el resultado se vea en el repositorio:

```yaml title=".github/workflows/test.yml"
name: Tests

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npx vitest run
```

`npm ci` instala exactamente las versiones de `package-lock.json`; `vitest run` termina con código 1 si algún test falla, y GitHub marca el commit en rojo. Con esto, un `README` con el *badge* del workflow demuestra que la entrega pasa sus pruebas.

## 🧩 Aplicación en el proyecto

Este recorrido es el patrón que aplicarás a tu aplicación del módulo:

- **Lógica en funciones puras** separadas de los componentes: más fácil de probar y de reutilizar.
- **Un test por componente** que cubra sus props, su interacción y sus callbacks.
- **Un test de integración** por flujo principal, con los componentes reales juntos.
- **`vitest run` en CI**, para que el estado de los tests sea visible en cada commit.

No hace falta cubrirlo todo desde el principio: empieza por las utilidades y el formulario principal, y añade tests cuando arregles un error (un test que reproduce el fallo y luego pasa es la mejor garantía de que no vuelve).

## Resumen rápido

| Capa | Qué se prueba | Herramienta |
| :--- | :--- | :--- |
| `utils/` | Entradas y salidas de funciones puras, casos límite, inmutabilidad | `describe` / `it` / `expect` |
| `components/` | Render según props, interacción, callbacks, estados vacío/deshabilitado | Testing Library + `userEvent` + `vi.fn` |
| `App` | Flujos completos del usuario con las piezas reales | Testing Library sin mocks |
| CI | Que todo pasa en cada push | `vitest run` en GitHub Actions |

## Convención práctica

<Steps>
	1. Escribe las **utilidades y sus tests primero**; los componentes se apoyan en ellas y quedan más simples.
	2. Da a cada elemento interactivo un **nombre accesible** (`<label>`, `aria-label`): es lo que buscan los tests y lo que necesitan los usuarios.
	3. Una **función auxiliar** en el test para las acciones repetidas (`addTask`), igual que harías en el código.
	4. El test de integración **no usa mocks**: si necesita uno, probablemente es un test de componente.
	5. Deja el **workflow de CI** desde el primer commit con tests; añadirlo después cuesta lo mismo y se olvida.
</Steps>
