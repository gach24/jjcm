Ya sabes la estructura de un test. Esta página cubre lo que necesitas para escribir los de verdad sobre las piezas de una aplicación React que no son componentes: utilidades, validaciones, servicios que llaman a la API y la lógica que hay detrás de un formulario. Es decir, qué **matchers** usar según lo que compares, cómo probar funciones **asíncronas** y las que **lanzan errores**, cómo evitar repetir la preparación de datos y cómo sustituir una dependencia (una llamada a la red, la fecha actual) por un **doble** controlado.

## Matchers: elegir la comparación correcta

`expect(valor)` devuelve un objeto con decenas de métodos. Estos cubren casi todo:

### Igualdad

| Matcher | Compara | Úsalo para |
| :--- | :--- | :--- |
| `toBe(x)` | `===` | primitivos: números, strings, booleanos |
| `toEqual(x)` | contenido, recursivamente | objetos y arrays |
| `toStrictEqual(x)` | contenido + `undefined` y clases | cuando importa la forma exacta |

```ts
expect(2 + 2).toBe(4);
expect("hola".toUpperCase()).toBe("HOLA");

expect({ id: 1, nombre: "Ana" }).toEqual({ id: 1, nombre: "Ana" });
expect([1, 2, 3]).toEqual([1, 2, 3]);

expect({ id: 1 }).toBe({ id: 1 }); // ❌ falla: son dos objetos distintos
```

<Aside type="caution" title="El error más frecuente">
	`toBe` con objetos o arrays **siempre falla** aunque tengan el mismo contenido, porque compara referencias. Regla: primitivos → `toBe`; todo lo demás → `toEqual`.
</Aside>

### Verdad, nulos y números

```ts
expect(usuario.activo).toBe(true);
expect(lista.length > 0).toBeTruthy();   // cualquier valor "verdadero"
expect(resultado).toBeNull();
expect(opcional).toBeUndefined();
expect(opcional).toBeDefined();

expect(precio).toBeGreaterThan(0);
expect(nota).toBeGreaterThanOrEqual(5);
expect(0.1 + 0.2).toBeCloseTo(0.3);      // decimales: nunca toBe
```

### Strings, arrays y objetos

```ts
expect("Hola, Ana").toContain("Ana");
expect("ana@correo.com").toMatch(/@/);

expect([1, 2, 3]).toContain(2);
expect([1, 2, 3]).toHaveLength(3);
expect(usuarios).toContainEqual({ id: 2, nombre: "Luis" }); // objeto dentro de array

expect(usuario).toHaveProperty("email");
expect(usuario).toHaveProperty("direccion.ciudad", "Oviedo");
expect(usuario).toMatchObject({ nombre: "Ana" });          // subconjunto de propiedades
```

### Negar: `.not`

Cualquier matcher se invierte con `.not`:

```ts
expect(lista).not.toContain(99);
expect(resultado).not.toBeNull();
```

## Probar que una función lanza un error

La función que lanza **no se llama directamente**: se envuelve en una arrow function para que sea `expect` quien la ejecute y capture el error.

La validación del título de una tarea, que usará el formulario de la app:

```ts title="src/utils/validar.ts"
export const TITULO_MAX = 100;

export function validarTitulo(titulo: string): string {
	const limpio = titulo.trim();
	if (limpio === "") throw new Error("El título no puede estar vacío");
	if (limpio.length > TITULO_MAX) throw new RangeError(`El título no puede superar ${TITULO_MAX} caracteres`);
	return limpio;
}
```

```ts title="src/utils/validar.test.ts"
import { describe, it, expect } from "vitest";
import { validarTitulo, TITULO_MAX } from "./validar";

describe("validarTitulo", () => {
	it("devuelve el título sin espacios sobrantes", () => {
		expect(validarTitulo("  Estudiar Vitest  ")).toBe("Estudiar Vitest");
	});

	it("lanza un error si está vacío", () => {
		expect(() => validarTitulo("   ")).toThrow("El título no puede estar vacío");
	});

	it("lanza RangeError si es demasiado largo", () => {
		expect(() => validarTitulo("a".repeat(TITULO_MAX + 1))).toThrow(RangeError);
	});

	it("no lanza con la longitud máxima exacta", () => {
		expect(() => validarTitulo("a".repeat(TITULO_MAX))).not.toThrow();
	});
});
```

`toThrow()` sin argumento comprueba solo que lanza; con un string, que el mensaje lo contiene; con una clase, que el error es de ese tipo.

## Código asíncrono

En una app React, las llamadas a la API se agrupan en **servicios**: funciones que hacen el `fetch` y devuelven datos con el tipo de la aplicación, para que los componentes no sepan nada de URLs. Se prueban marcando el test como `async` y usando `await`, exactamente como en la aplicación:

```ts title="src/services/usuarios.ts"
export interface Usuario {
	id: number;
	nombre: string;
}

export async function obtenerUsuario(id: number): Promise<Usuario> {
	const res = await fetch(`https://jsonplaceholder.typicode.com/users/${id}`);
	if (!res.ok) throw new Error(`HTTP ${res.status}`);
	const data = await res.json();
	return { id: data.id, nombre: data.name };
}
```

```ts title="src/services/usuarios.test.ts"
import { describe, it, expect } from "vitest";
import { obtenerUsuario } from "./usuarios";

describe("obtenerUsuario", () => {
	it("devuelve el usuario con id y nombre", async () => {
		const usuario = await obtenerUsuario(1);
		expect(usuario).toEqual({ id: 1, nombre: "Leanne Graham" });
	});

	it("rechaza si el usuario no existe", async () => {
		await expect(obtenerUsuario(999)).rejects.toThrow("HTTP 404");
	});
});
```

Para promesas, `expect(promesa).resolves.matcher()` y `expect(promesa).rejects.matcher()`; **siempre con `await` delante**, o el test termina antes de que la promesa se resuelva.

<Aside type="caution" title="Este test depende de internet">
	Funciona, pero llama a un servidor real: es lento, falla sin conexión y no controlas la respuesta. En el siguiente apartado verás cómo sustituir `fetch` por un doble. Para aprender la mecánica de `async` está bien; en un proyecto real, no.
</Aside>

## Preparar y limpiar: `beforeEach`

Cuando varios tests necesitan los mismos datos iniciales, se crean en un `beforeEach`, que se ejecuta **antes de cada** `it`:

Un carrito de compra que mantiene sus líneas en una variable privada, como el que alimentaría un componente de resumen de pedido:

```ts title="src/utils/carrito.ts"
export interface LineaCarrito {
	producto: string;
	precio: number;
	cantidad: number;
}

export function crearCarrito() {
	const lineas: LineaCarrito[] = [];

	return {
		agregar(producto: string, precio: number, cantidad: number): void {
			lineas.push({ producto, precio, cantidad });
		},
		total(): number {
			return lineas.reduce((acc, linea) => acc + linea.precio * linea.cantidad, 0);
		},
		vaciar(): void {
			lineas.length = 0;
		},
	};
}

export type Carrito = ReturnType<typeof crearCarrito>;
```

```ts title="src/utils/carrito.test.ts"
import { describe, it, expect, beforeEach } from "vitest";
import { crearCarrito, type Carrito } from "./carrito";

describe("Carrito", () => {
	let carrito: Carrito;

	beforeEach(() => {
		carrito = crearCarrito();
		carrito.agregar("Teclado", 49.99, 1);
	});

	it("calcula el total", () => {
		expect(carrito.total()).toBeCloseTo(49.99);
	});

	it("suma al agregar otro producto", () => {
		carrito.agregar("Ratón", 19.99, 2);
		expect(carrito.total()).toBeCloseTo(89.97);
	});

	it("queda vacío al vaciar", () => {
		carrito.vaciar();
		expect(carrito.total()).toBe(0);
	});
});
```

Cada test recibe un carrito **nuevo**: lo que haga el segundo no afecta al tercero. También existen `afterEach`, `beforeAll` y `afterAll`; los dos últimos se ejecutan una sola vez por `describe`.

<Aside type="tip" title="Tests independientes">
	Un test nunca debe depender de que otro se haya ejecutado antes. Vitest puede ejecutarlos en otro orden o en paralelo; si comparten estado, fallarán de forma intermitente y perderás horas buscando por qué.
</Aside>

## Dobles de prueba: `vi.fn()`

`vi.fn()` crea una **función falsa** (*mock*) que no hace nada pero recuerda cada llamada que recibe. En React, los componentes avisan a sus padres mediante **callbacks** pasados por props (`onAdd`, `onSubmit`…); `vi.fn` sirve para comprobar que se llaman cuando toca y con qué. Esta es la lógica que hay detrás del envío del formulario de tareas, separada del componente:

```ts title="src/utils/formulario.ts"
export function enviarTarea(titulo: string, onGuardar: (titulo: string) => void): void {
	const limpio = titulo.trim();
	if (limpio === "") return;
	onGuardar(limpio);
}
```

```ts title="src/utils/formulario.test.ts"
import { describe, it, expect, vi } from "vitest";
import { enviarTarea } from "./formulario";

describe("enviarTarea", () => {
	it("llama a onGuardar con el título limpio", () => {
		const onGuardar = vi.fn();
		enviarTarea("  Estudiar Vitest  ", onGuardar);

		expect(onGuardar).toHaveBeenCalledTimes(1);
		expect(onGuardar).toHaveBeenCalledWith("Estudiar Vitest");
	});

	it("no llama a onGuardar si el título está vacío", () => {
		const onGuardar = vi.fn();
		enviarTarea("   ", onGuardar);

		expect(onGuardar).not.toHaveBeenCalled();
	});
});
```

Matchers para mocks: `toHaveBeenCalled()`, `toHaveBeenCalledTimes(n)`, `toHaveBeenCalledWith(args)`, `toHaveBeenLastCalledWith(args)`. Un mock también puede **devolver** un valor: `vi.fn(() => 42)` o `vi.fn().mockReturnValue(42)`.

### Sustituir `fetch`

Con `vi.spyOn` reemplazas temporalmente una función global por un mock que devuelve lo que tú decidas. Así el test de `obtenerUsuario` deja de depender de la red:

```ts title="src/services/usuarios.test.ts"
import { describe, it, expect, vi, afterEach } from "vitest";
import { obtenerUsuario } from "./usuarios";

afterEach(() => {
	vi.restoreAllMocks(); // devuelve fetch a su estado original
});

describe("obtenerUsuario (sin red)", () => {
	it("devuelve el usuario con id y nombre", async () => {
		vi.spyOn(globalThis, "fetch").mockResolvedValue(
			new Response(JSON.stringify({ id: 1, name: "Ana" }), { status: 200 }),
		);

		const usuario = await obtenerUsuario(1);
		expect(usuario).toEqual({ id: 1, nombre: "Ana" });
		expect(fetch).toHaveBeenCalledWith("https://jsonplaceholder.typicode.com/users/1");
	});

	it("rechaza si la respuesta no es ok", async () => {
		vi.spyOn(globalThis, "fetch").mockResolvedValue(new Response("", { status: 404 }));

		await expect(obtenerUsuario(999)).rejects.toThrow("HTTP 404");
	});
});
```

El test ahora es instantáneo, funciona sin conexión y prueba **tu** código (que construyes bien la URL y tratas el `status`), no el servidor de otro.

<Aside type="note" title="Hasta aquí con los mocks">
	Vitest permite mucho más: sustituir módulos enteros (`vi.mock`), controlar el reloj (`vi.useFakeTimers`), espiar métodos de objetos. Para este módulo, `vi.fn` y `vi.spyOn` sobre `fetch` cubren lo necesario; el resto está en la referencia enlazada abajo.
</Aside>

## Organizar: `it.each`, `skip` y `only`

Cuando el mismo test se repite con distintos datos, `it.each` evita copiar y pegar:

```ts title="src/utils/format.test.ts"
import { describe, it, expect } from "vitest";
import { pluralizar } from "./format";

describe("pluralizar", () => {
	it.each([
		[0, "0 tareas"],
		[1, "1 tarea"],
		[2, "2 tareas"],
		[15, "15 tareas"],
	])("con %i devuelve %s", (cantidad, esperado) => {
		expect(pluralizar(cantidad, "tarea", "tareas")).toBe(esperado);
	});
});
```

Y para trabajar: `it.skip` salta un test (aparece como omitido), `it.only` ejecuta solo ese (útil mientras lo escribes; **nunca** lo dejes en un commit), `it.todo("nombre")` deja anotado un test pendiente.

## 🧩 Aplicación en el proyecto

En tu aplicación React, estos son los tests que escribirás con lo visto aquí:

- **Utilidades de la interfaz** (`toBe`, `toEqual`, `toBeCloseTo`): `formatearPrecio`, `pluralizar`, filtrados y ordenaciones de listas que luego pinta un componente.
- **Validaciones de formularios** (`toThrow`): `validarTitulo` y cualquier regla sobre lo que escribe el usuario.
- **Servicios que llaman a la API** (`async` + `vi.spyOn(fetch)`): que construyen la URL correcta, que convierten la respuesta al tipo de tu app, que tratan los errores HTTP.
- **Callbacks** (`vi.fn`): la lógica que decide cuándo avisar al padre. Es el puente hacia probar componentes, donde esos callbacks son las props `onAdd`, `onSubmit`, `onChange`…

## Resumen rápido

| Qué compruebas | Matcher |
| :--- | :--- |
| Primitivo | `toBe` |
| Objeto o array | `toEqual` |
| Decimal | `toBeCloseTo` |
| Contiene | `toContain`, `toMatch`, `toHaveProperty`, `toMatchObject` |
| Lanza error | `expect(() => f()).toThrow(msg \| Clase)` |
| Promesa | `await expect(p).resolves / .rejects` |
| Mock llamado | `toHaveBeenCalled`, `toHaveBeenCalledWith`, `toHaveBeenCalledTimes` |
| Preparar | `beforeEach`, `afterEach`; limpiar mocks con `vi.restoreAllMocks()` |
| Repetir con datos | `it.each([...])("nombre %s", (a, b) => …)` |

## Convención práctica

<Steps>
	1. **`toBe` para primitivos, `toEqual` para objetos**, `toBeCloseTo` para decimales. Elegir mal el matcher produce tests que fallan sin motivo o que pasan sin comprobar nada.
	2. Prueba el **caso normal, los límites y el error** de cada función: tres tests mínimos.
	3. Ningún test unitario toca **la red ni el disco**: sustituye `fetch` con `vi.spyOn` y restaura en `afterEach`.
	4. Prepara datos en `beforeEach`; cada test empieza de cero.
	5. Antes de commitear, busca `.only` en los tests: si queda uno, el resto no se está ejecutando.
</Steps>
