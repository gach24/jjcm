Una **prueba automatizada** es código que ejecuta tu código y comprueba que el resultado es el esperado. Todos los ejemplos de esta unidad viven dentro de la aplicación React `task-app` de la página anterior: utilidades que usa la interfaz, servicios que piden datos y componentes. En lugar de abrir la app, pulsar botones y mirar si "parece que funciona", escribes una vez la comprobación y la ejecutas cuantas veces quieras, en segundos. **Vitest** es el *test runner* pensado para proyectos Vite: usa la misma configuración y la misma forma de importar que tu app, por lo que no hay que configurar casi nada.

<CardGrid stagger>
	<Card title="¿Qué es?" icon="rocket">
		Un programa que busca archivos `*.test.ts`, ejecuta las funciones que contienen y te dice cuáles pasan y cuáles fallan.
	</Card>
	<Card title="¿Para qué sirve?" icon="approve-check">
		Detectar que algo se ha roto **antes** de que lo vea el usuario, y poder cambiar código con confianza.
	</Card>
	<Card title="¿Qué necesitas?" icon="open-book">
		Un proyecto Vite (React o no). Vitest se instala encima y reutiliza `vite.config.ts`.
	</Card>
</CardGrid>

## Por qué probar

Sin pruebas, cada cambio obliga a comprobar a mano todo lo que podría haberse visto afectado, y nadie lo hace de forma completa. Las consecuencias habituales:

- Arreglas un fallo y rompes otra cosa sin darte cuenta ("regresión").
- Te da miedo tocar código que funciona, aunque esté mal escrito.
- Los errores llegan al usuario, que es la forma más cara de encontrarlos.

Con pruebas, `npm test` responde en segundos a la pregunta "¿sigue funcionando todo lo que funcionaba?". No sustituyen a probar la app a mano, pero cubren la parte repetitiva y aburrida, que es precisamente la que se deja de hacer.

<Aside type="tip" title="Tres niveles de prueba">
	**Unitarias**: una función o un componente aislado (Vitest). **De integración**: varias piezas juntas, por ejemplo un formulario con su lista (Vitest + Testing Library). **De extremo a extremo (E2E)**: la aplicación real en un navegador real (Playwright, el siguiente subapartado). En este módulo tocarás las tres.
</Aside>

## Por qué Vitest

Hay otros runners (Jest es el más conocido), pero en un proyecto Vite, Vitest tiene ventajas claras:

| Ventaja | Qué significa |
| :--- | :--- |
| **Misma configuración** | Lee `vite.config.ts`: alias, plugins y TypeScript funcionan igual que en la app |
| **Sin transpilar aparte** | TypeScript y JSX se procesan con el mismo motor que Vite; no hay `babel.config` ni `ts-jest` |
| **Rápido** | Ejecuta solo los tests afectados por cada cambio y los corre en paralelo |
| **API compatible con Jest** | `describe`, `it`, `expect`… son iguales; lo que aprendas sirve en ambos |
| **Modo watch e interfaz web** | Relanza al guardar y tiene un panel en el navegador (`--ui`) |

## Instalación

Sobre el proyecto `task-app` de la página anterior (o cualquier proyecto Vite + React):

```bash
npm install -D vitest
```

<Aside type="tip" title="¿Todavía no tienes un proyecto?">
	La página anterior, [Preparar el proyecto](/jjcm/di/units/testing/vitest/00-project-setup/), explica desde cero cómo crear un proyecto React con Vite, qué archivos genera y cómo arranca. Hazla primero y vuelve aquí.
</Aside>

Añade el script a `package.json`:

```json title="package.json" {4}
{
	"scripts": {
		"dev": "vite",
		"test": "vitest",
		"build": "tsc -b && vite build"
	}
}
```

No hace falta ningún archivo de configuración para empezar: Vitest encuentra solo los archivos cuyo nombre termina en `.test.ts`, `.test.tsx`, `.spec.ts` o `.spec.tsx`.

<Aside type="note" title="Qué es `-D`">
	`-D` (o `--save-dev`) instala el paquete como **dependencia de desarrollo**: se usa para programar y probar, pero no forma parte de la aplicación que se despliega. Todas las herramientas de prueba van ahí.
</Aside>

## Tu primer test

En una aplicación React, lo primero que se prueba son las **utilidades** que usa la interfaz: pequeñas funciones puras que formatean o calculan algo que luego pinta un componente. Crea `src/utils/format.ts` con dos que necesitará la app de tareas: el precio de un producto en una tarjeta y el texto del contador de pendientes.

```ts title="src/utils/format.ts"
export function formatPrice(price: number): string {
	return `${price.toFixed(2).replace(".", ",")} €`;
}

export function pluralize(count: number, singular: string, plural: string): string {
	return `${count} ${count === 1 ? singular : plural}`;
}
```

Y su archivo de pruebas, **al lado**, con el mismo nombre más `.test`:

```ts title="src/utils/format.test.ts"
import { describe, it, expect } from "vitest";
import { formatPrice, pluralize } from "./format";

describe("formatPrice", () => {
	it("formats with two decimals, a comma and the euro sign", () => {
		expect(formatPrice(19.99)).toBe("19,99 €");
	});

	it("adds decimals to integers", () => {
		expect(formatPrice(5)).toBe("5,00 €");
	});
});

describe("pluralize", () => {
	it("uses the singular for 1", () => {
		expect(pluralize(1, "pending task", "pending tasks")).toBe("1 pending task");
	});

	it("uses the plural for 0 and for several", () => {
		expect(pluralize(0, "pending task", "pending tasks")).toBe("0 pending tasks");
		expect(pluralize(3, "pending task", "pending tasks")).toBe("3 pending tasks");
	});
});
```

Las tres piezas que se repiten en todo test:

<Steps>
	1. **`describe`** agrupa pruebas relacionadas (normalmente, una función o un componente). Es solo organización: aparece como título en la salida.
	2. **`it`** (o `test`, son sinónimos) define **una** prueba, con una frase que describe el comportamiento esperado. Si falla, esa frase es lo primero que lees.
	3. **`expect(valor).matcher(esperado)`** es la **aserción**: la comprobación concreta. `toBe` compara con `===`; en la siguiente página verás el resto de *matchers*.
</Steps>

## Ejecutar los tests

```bash
npm test
```

Vitest arranca en **modo watch**: ejecuta todo, muestra el resultado y se queda esperando. Cada vez que guardas un archivo, relanza solo los tests afectados.

```txt
 ✓ src/utils/format.test.ts (4 tests) 3ms
   ✓ formatPrice > formats with two decimals, a comma and the euro sign
   ✓ formatPrice > adds decimals to integers
   ✓ pluralize > uses the singular for 1
   ✓ pluralize > uses the plural for 0 and for several

 Test Files  1 passed (1)
      Tests  4 passed (4)
```

Prueba a romper algo: cambia `toFixed(2)` por `toFixed(1)`, guarda y mira la salida. Vitest señala el test que falla, la línea exacta y la diferencia entre lo esperado y lo obtenido:

```txt
 FAIL  src/utils/format.test.ts > formatPrice > formats with two decimals, a comma and the euro sign
AssertionError: expected '19,9 €' to be '19,99 €' // Object.is equality

- Expected   "19,99 €"
+ Received   "19,9 €"
```

Otros modos de ejecución que usarás:

| Comando | Qué hace |
| :--- | :--- |
| `npx vitest run` | Ejecuta una vez y termina (para CI y para scripts) |
| `npx vitest --ui` | Abre un panel en el navegador con los tests, su estado y su salida (instala `@vitest/ui`) |
| `npx vitest run format` | Solo los archivos cuya ruta contenga `format` |
| `npx vitest run --coverage` | Informe de qué líneas se han ejecutado durante los tests (instala `@vitest/coverage-v8`) |

<Aside type="caution" title="Watch en la terminal, run en CI">
	`vitest` a secas no termina nunca: es para desarrollar. En un script de build o en GitHub Actions usa siempre `vitest run`, que ejecuta una vez y devuelve un código de salida (0 si todo pasa, 1 si algo falla).
</Aside>

## Dónde colocar los tests

Dos convenciones válidas; en este módulo usaremos la primera:

- **Junto al archivo probado**: `format.ts` y `format.test.ts` en la misma carpeta. Es fácil ver qué tiene pruebas y qué no, y al mover el archivo se mueve su test.
- **Carpeta `tests/` o `__tests__/`** aparte, con la misma estructura que `src/`. Separa el código de producción, a cambio de tener que buscar.

Vitest excluye por defecto `node_modules/` y `dist/`, así que no hay que configurar rutas.

## 🧩 Aplicación en el proyecto

En el contexto de este módulo, Vitest se usa para:

- **Probar la lógica pura** de tu aplicación React: funciones de utilidad, cálculos, transformaciones de datos, validaciones. Es lo más barato de probar y donde más errores se esconden.
- **Probar componentes** con Testing Library (tercera página): que un formulario llame a su callback, que una lista muestre sus elementos.
- **Demostrar que la entrega funciona**: un `npm test` en verde, visible en el repositorio, vale más que una captura de pantalla.

El objetivo no es cubrir el 100 % del código, sino que las partes con lógica tengan pruebas y que ejecutarlas sea un hábito antes de cada commit.

## Resumen rápido

| Concepto | Detalle |
| :--- | :--- |
| **Vitest** | Test runner para proyectos Vite; API compatible con Jest |
| **Instalar** | `npm install -D vitest` + script `"test": "vitest"` |
| **Archivo de test** | `nombre.test.ts` junto al archivo probado |
| **Estructura** | `describe` (grupo) → `it` (prueba) → `expect` (aserción) |
| **Ejecutar** | `npm test` (watch) · `npx vitest run` (una vez) · `--ui` · `--coverage` |

## Convención práctica

<Steps>
	1. Nombra cada `it` como una **frase que describe el comportamiento** ("devuelve 0 con lista vacía"), no la implementación ("llama a reduce").
	2. Un `it` comprueba **una cosa**. Si tiene cinco `expect` sobre asuntos distintos, son cinco tests.
	3. Coloca el test **junto al archivo** que prueba y con el mismo nombre más `.test`.
	4. Ejecuta `npm test` **antes de cada commit**; un test que falla no se commitea.
	5. Prueba primero lo que tiene **lógica** (cálculos, condiciones); dejar sin test un componente que solo pinta texto es aceptable.
</Steps>
