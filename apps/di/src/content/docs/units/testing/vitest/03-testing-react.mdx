Un componente React se prueba **como lo usaría una persona**: se renderiza, se busca en pantalla un botón o un campo por su texto, se interactúa y se comprueba qué aparece. **Testing Library** es la librería que da ese enfoque sobre Vitest; su principio es que los tests no deben conocer la implementación (nombres de clases, estado interno), solo lo que el usuario ve y hace.

	</Card>

## Instalación y configuración

Sobre el proyecto con Vitest ya instalado:

```bash
npm install -D jsdom @testing-library/react @testing-library/dom @testing-library/user-event @testing-library/jest-dom
```

| Paquete | Para qué |
| :--- | :--- |
| `jsdom` | Un DOM en Node: `document`, `window`, eventos. Sin él, `render` no tiene dónde montar |
| `@testing-library/react` | `render`, `screen`, `cleanup` para React |
| `@testing-library/dom` | Dependencia de la anterior (las consultas `getBy*`) |
| `@testing-library/user-event` | Simula al usuario: teclear, pulsar, seleccionar |
| `@testing-library/jest-dom` | Matchers para el DOM: `toBeInTheDocument`, `toBeDisabled`, `toHaveValue`… |

Vitest necesita saber que debe usar jsdom y cargar los matchers. Se configura en `vite.config.ts`, el mismo archivo de Vite:

```ts title="vite.config.ts" {1,7-10}
/// <reference types="vitest/config" />
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
	plugins: [react()],
	test: {
		environment: "jsdom",
		setupFiles: "./src/setupTests.ts",
	},
});
```

```ts title="src/setupTests.ts"
import "@testing-library/jest-dom/vitest";
import { cleanup } from "@testing-library/react";
import { afterEach } from "vitest";

afterEach(() => {
	cleanup();
});
```

La primera línea del `vite.config.ts` (`/// <reference …>`) le dice a TypeScript que la propiedad `test` existe. El `setupFiles` se ejecuta antes de cada archivo de test y registra los matchers de jest-dom en `expect`.

El `afterEach(cleanup)` **desmonta** los componentes renderizados al terminar cada test. Testing Library lo haría sola si `afterEach` fuera una función global, pero en Vitest no lo es (salvo que actives `globals: true`), así que hay que registrarlo. Sin esta línea, los componentes de un test siguen en el DOM durante el siguiente y las consultas fallan con *Found multiple elements*.

<Aside type="note" title="Por qué jsdom">
	Vitest corre en Node, donde no hay navegador. jsdom implementa el DOM en JavaScript con fidelidad suficiente para renderizar componentes y disparar eventos. No pinta nada ni calcula estilos: para comprobar cómo se **ve** algo está Playwright.
</Aside>

## Un componente para probar

Los componentes de esta página van en `src/components/` (crea la carpeta si no existe), cada uno con su test al lado.

```tsx title="src/components/Counter.tsx"
import { useState } from "react";

interface Props {
	initial?: number;
	onChange?: (value: number) => void;
}

export function Counter({ initial = 0, onChange }: Props) {
	const [value, setValue] = useState(initial);

	function update(next: number) {
		setValue(next);
		onChange?.(next);
	}

	return (
		<div>
			<p>Value: {value}</p>
			<button onClick={() => update(value - 1)} disabled={value <= 0}>
				Decrement
			</button>
			<button onClick={() => update(value + 1)}>Increment</button>
		</div>
	);
}
```

## El primer test de componente

```tsx title="src/components/Counter.test.tsx"
import { describe, it, expect, vi } from "vitest";
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { Counter } from "./Counter";

describe("Counter", () => {
	it("shows the initial value", () => {
		render(<Counter initial={5} />);
		expect(screen.getByText("Value: 5")).toBeInTheDocument();
	});

	it("increments when Increment is clicked", async () => {
		const user = userEvent.setup();
		render(<Counter />);

		await user.click(screen.getByRole("button", { name: "Increment" }));

		expect(screen.getByText("Value: 1")).toBeInTheDocument();
	});

	it("disables Decrement at zero", () => {
		render(<Counter initial={0} />);
		expect(screen.getByRole("button", { name: "Decrement" })).toBeDisabled();
	});

	it("notifies the change through onChange", async () => {
		const user = userEvent.setup();
		const onChange = vi.fn();
		render(<Counter initial={2} onChange={onChange} />);

		await user.click(screen.getByRole("button", { name: "Increment" }));

		expect(onChange).toHaveBeenCalledWith(3);
	});
});
```

El archivo es `.tsx` porque contiene JSX. El patrón de cada test es siempre el mismo:

<Steps>
	1. **Renderizar** el componente con las props del caso: `render(<Counter initial={5} />)`.
	2. **Encontrar** el elemento con `screen`: el botón "Increment", el texto "Value: 5".
	3. **Interactuar**, si procede, con `user.click`, `user.type`… siempre con `await`.
	4. **Comprobar** el resultado con un matcher de jest-dom o con `vi.fn` si lo que importa es un callback.
</Steps>

## Consultas: encontrar elementos como el usuario

`screen` ofrece consultas por distintos criterios. El orden de preferencia importa, porque un test que busca por rol sigue funcionando aunque cambies el HTML, y uno que busca por clase CSS no:

| Consulta | Encuentra por | Ejemplo |
| :--- | :--- | :--- |
| `getByRole` | rol accesible y nombre | `getByRole("button", { name: "Save" })` |
| `getByLabelText` | la `<label>` de un campo | `getByLabelText("Email")` |
| `getByPlaceholderText` | el placeholder | `getByPlaceholderText("Search…")` |
| `getByText` | el texto visible | `getByText("No results")` |
| `getByDisplayValue` | el valor actual de un input | `getByDisplayValue("Ana")` |
| `getByTestId` | `data-testid="…"` | último recurso |

Roles habituales: `button`, `textbox` (input de texto y textarea), `checkbox`, `link`, `heading`, `list` y `listitem`, `option`. El `name` de un `button` es su texto; el de un `textbox`, su `<label>`.

<Aside type="tip" title="Si no encuentras el rol">
	`screen.logTestingPlaygroundURL()` dentro de un test imprime un enlace que abre el HTML renderizado en *Testing Playground*, donde pulsas un elemento y te dice qué consulta usar. Y `screen.debug()` imprime el HTML actual en la terminal.
</Aside>

### `screen` o `container`

`render` devuelve un objeto con, entre otras cosas, `container`: el `div` en el que se ha montado el componente. En tutoriales antiguos verás consultas sobre él, pero no es lo recomendado:

| | `screen` | `container` |
| :--- | :--- | :--- |
| Qué es | El `document.body` completo, con las mismas consultas (`getByRole`, `getByText`…) | El `div` que envuelve lo que ha renderizado **este** `render` |
| Cómo busca | Como el usuario: por rol, etiqueta o texto | Como el DOM: `container.querySelector(".card")`, `container.firstChild` |
| Úsalo para | Casi todo. No hace falta guardar el resultado de `render` | Casos sin alternativa accesible: comprobar que no se renderiza **nada** (`container` vacío) o inspeccionar un nodo sin rol ni texto, como un `<svg>` o un `<hr>` |

```tsx
const { container } = render(<Divider />);
expect(container.querySelector("hr")).toBeInTheDocument(); // no role, no text

render(<Empty />);
expect(screen.queryByRole("list")).not.toBeInTheDocument(); // the normal way
```

Si te sorprendes escribiendo `container.querySelector` para un botón o un título, vuelve a `screen`: el test está mirando la implementación en lugar de lo que ve el usuario, y se romperá en cuanto cambies una clase.

### `getBy`, `queryBy` y `findBy`

Cada consulta tiene tres variantes según qué esperas:

| Prefijo | Si no existe | Úsalo para |
| :--- | :--- | :--- |
| `getBy` | **lanza error** | elementos que deben estar |
| `queryBy` | devuelve `null` | comprobar que algo **no** está |
| `findBy` | espera hasta 1 s, luego lanza | elementos que aparecen **después** (async) |

```tsx
expect(screen.getByText("Saved")).toBeInTheDocument();      // must be present
expect(screen.queryByText("Error")).not.toBeInTheDocument();   // must not be present
expect(await screen.findByText("Loaded")).toBeInTheDocument(); // will appear
```

Las versiones en plural (`getAllByRole`, `queryAllByText`…) devuelven arrays, para listas.

## Interactuar: `userEvent`

`userEvent.setup()` crea un "usuario" que dispara la secuencia real de eventos (`pointerdown`, `focus`, `keydown`, `input`…). Sus métodos son asíncronos: **siempre `await`**.

```tsx
const user = userEvent.setup();

await user.click(screen.getByRole("button", { name: "Add" }));
await user.type(screen.getByLabelText("Name"), "Ana");
await user.clear(screen.getByLabelText("Name"));
await user.selectOptions(screen.getByRole("combobox"), "editor");
await user.keyboard("{Enter}");
```

<Aside type="caution" title="`fireEvent` existe, pero prefiere `userEvent`">
	Verás `fireEvent.click(boton)` en tutoriales antiguos. Dispara un único evento sintético y no reproduce el comportamiento real (no mueve el foco, no respeta `disabled`). `userEvent` es la recomendación actual de Testing Library.
</Aside>

## Probar un hook: `renderHook` y `act`

Un **hook personalizado** (una función `useX` que llama a `useState`, `useEffect`…) solo puede ejecutarse dentro de un componente: fuera, React lanza *Invalid hook call*. Para probarlo sin montar ningún componente real, Testing Library trae `renderHook`, que lo envuelve en un componente invisible y te deja mirar lo que devuelve.

### Un hook para probar

```ts title="src/hooks/useCounter.ts"
import { useState } from "react";

export function useCounter(initial = 0, step = 1) {
	const [count, setCount] = useState(initial);

	const increment = () => setCount((c) => c + step);
	const decrement = () => setCount((c) => Math.max(0, c - step));
	const reset = () => setCount(initial);

	return { count, increment, decrement, reset };
}
```

No tiene JSX, así que su archivo y el de su test son `.ts`, no `.tsx`.

### El test

```ts title="src/hooks/useCounter.test.ts"
import { act, renderHook } from "@testing-library/react";
import { describe, expect, it } from "vitest";
import { useCounter } from "./useCounter";

describe("useCounter", () => {
	it("starts with the initial value", () => {
		const { result } = renderHook(() => useCounter(5));

		expect(result.current.count).toBe(5);
	});

	it("increments by the step", () => {
		const { result } = renderHook(() => useCounter(0, 2));

		act(() => result.current.increment());

		expect(result.current.count).toBe(2);
	});

	it("never goes below zero", () => {
		const { result } = renderHook(() => useCounter(1));

		act(() => result.current.decrement());
		act(() => result.current.decrement());

		expect(result.current.count).toBe(0);
	});

	it("resets to the initial value", () => {
		const { result } = renderHook(() => useCounter(3));

		act(() => result.current.increment());
		act(() => result.current.reset());

		expect(result.current.count).toBe(3);
	});
});
```

Las tres piezas, una por una:

| Pieza | Qué es | Qué hace |
| :--- | :--- | :--- |
| `renderHook(() => useCounter(5))` | La función que **monta** el hook | Crea un componente de prueba que llama a la función que le pasas en cada renderizado, igual que haría `App`. Devuelve un objeto con `result`, `rerender` y `unmount` |
| `result.current` | El **último valor devuelto** por el hook | Es lo que el hook ha devuelto en el renderizado más reciente: aquí `{ count, increment, decrement, reset }`. Cada vez que el estado cambia, el componente se vuelve a renderizar y `result.current` apunta al objeto nuevo |
| `act(() => …)` | Un envoltorio para **cambiar el estado** | Ejecuta la función y **espera a que React procese** el cambio y renderice antes de seguir. Sin `act`, la aserción podría ejecutarse antes de que `count` se haya actualizado |

Es el equivalente, para un hook, de lo que hacen `render` y `userEvent` con un componente: `renderHook` monta, `act` interactúa y `result.current` es lo que "se ve".

<Aside type="caution" title="`result.current` se lee después, no antes">
	Un error habitual:

	```ts
	const { count, increment } = result.current; // ✗ copia del primer renderizado
	act(() => increment());
	expect(count).toBe(1); // falla: count sigue siendo 0
	```

	`count` es un número copiado en ese momento; no cambia cuando el hook se vuelve a ejecutar. Lee siempre `result.current.count` **en la aserción**, después del `act`. Las funciones (`increment`) sí pueden copiarse si el hook las mantiene estables, pero es más seguro leerlas también desde `result.current`.
</Aside>

<Aside type="note" title="Si olvidas `act`">
	Vitest no falla, pero avisa: *Warning: An update to TestComponent inside a test was not wrapped in act(...)*. Y la aserción puede fallar de forma intermitente. Cualquier llamada que acabe en un `setState` va dentro de `act`. Las acciones de `userEvent` ya lo hacen por dentro; con un hook lo escribes tú.
</Aside>

### Argumentos que cambian: `rerender`

Si el hook recibe argumentos y el test necesita cambiarlos, se pasan como `initialProps` y se vuelven a renderizar con `rerender`:

```ts
const { result, rerender } = renderHook(
	({ initial }) => useCounter(initial),
	{ initialProps: { initial: 0 } }
);

rerender({ initial: 10 });

act(() => result.current.reset());
expect(result.current.count).toBe(10);
```

### Hooks con efectos

Si el hook usa `useEffect` para hablar con algo externo (`localStorage`, `document.title`, un temporizador), el test prepara ese exterior antes y lo comprueba después, exactamente como con un componente:

```ts
localStorage.setItem("count", "7");

const { result } = renderHook(() => usePersistentCounter());

expect(result.current.count).toBe(7);

act(() => result.current.increment());

expect(localStorage.getItem("count")).toBe("8");
```

Y `unmount()` ejecuta las limpiezas de los efectos, para comprobar que un escuchador o un temporizador se retira.

### Qué probar en un hook

- **Lo que devuelve** con distintos valores iniciales.
- **Cada acción** y su efecto en el estado, de una en una.
- **Los límites y casos raros**: valores mínimos y máximos, llamar dos veces, llamar sin elementos.
- **Lo externo**: qué lee y qué escribe en `localStorage`, en el DOM o en una API (simulada).

No se prueba **cómo** lo hace: ni cuántos `useState` tiene ni cómo se llaman. Los componentes que usan el hook se prueban aparte, pasándoles funciones falsas (`vi.fn()`) en lugar del hook real.

## Un formulario completo

```tsx title="src/components/LoginForm.tsx"
import { useState, type FormEvent } from "react";

interface Props {
	onLogin: (data: { email: string; password: string }) => void;
}

export function LoginForm({ onLogin }: Props) {
	const [email, setEmail] = useState("");
	const [password, setPassword] = useState("");
	const [error, setError] = useState("");

	function handleSubmit(e: FormEvent) {
		e.preventDefault();
		if (!email.includes("@")) {
			setError("Enter a valid email");
			return;
		}
		setError("");
		onLogin({ email, password });
	}

	return (
		<form onSubmit={handleSubmit} noValidate>
			<label htmlFor="email">Email</label>
			<input id="email" type="email" value={email} onChange={e => setEmail(e.target.value)} />

			<label htmlFor="password">Password</label>
			<input id="password" type="password" value={password} onChange={e => setPassword(e.target.value)} />

			{error && <p role="alert">{error}</p>}

			<button type="submit">Sign in</button>
		</form>
	);
}
```

```tsx title="src/components/LoginForm.test.tsx"
import { describe, it, expect, vi } from "vitest";
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { LoginForm } from "./LoginForm";

describe("LoginForm", () => {
	it("submits the data when the email is valid", async () => {
		const user = userEvent.setup();
		const onLogin = vi.fn();
		render(<LoginForm onLogin={onLogin} />);

		await user.type(screen.getByLabelText("Email"), "ana@example.com");
		await user.type(screen.getByLabelText("Password"), "secret");
		await user.click(screen.getByRole("button", { name: "Sign in" }));

		expect(onLogin).toHaveBeenCalledWith({ email: "ana@example.com", password: "secret" });
		expect(screen.queryByRole("alert")).not.toBeInTheDocument();
	});

	it("shows an error and does not submit when the email is invalid", async () => {
		const user = userEvent.setup();
		const onLogin = vi.fn();
		render(<LoginForm onLogin={onLogin} />);

		await user.type(screen.getByLabelText("Email"), "ana");
		await user.click(screen.getByRole("button", { name: "Sign in" }));

		expect(screen.getByRole("alert")).toHaveTextContent("Enter a valid email");
		expect(onLogin).not.toHaveBeenCalled();
	});
});
```

Fíjate en que el test no sabe nada de `useState`, ni de cómo se llama la variable `error`: solo que al escribir y pulsar, aparece un mensaje de alerta o se llama al callback. Puedes reescribir el componente por dentro y el test sigue valiendo.

<Aside type="note" title="Por qué `noValidate` en el formulario">
	Un `<input type="email">` con un valor no válido hace que el navegador **bloquee el envío** y muestre su propio aviso, sin que llegue a ejecutarse `onSubmit`. jsdom imita ese comportamiento, así que el segundo test nunca vería el mensaje de error del componente. `noValidate` desactiva la validación nativa y deja el control (y el mensaje) en manos del componente, que es lo que queremos probar.
</Aside>

## Matchers de jest-dom

Los que más usarás:

| Matcher | Comprueba |
| :--- | :--- |
| `toBeInTheDocument()` | que el elemento existe |
| `toBeVisible()` | que además no está oculto |
| `toBeDisabled()` / `toBeEnabled()` | estado de botones y campos |
| `toHaveValue(x)` | valor de un input |
| `toHaveTextContent(texto)` | texto de un elemento |
| `toBeChecked()` | checkbox o radio marcado |
| `toHaveAttribute(nombre, valor)` | cualquier atributo |
| `toHaveClass(clase)` | clase CSS (evítalo salvo que la clase sea el comportamiento) |

## Qué probar en un componente (y qué no)

<Tabs>
	<TabItem label="Sí">
		- Que **renderiza lo que recibe** por props (nombre, lista, estado vacío).
		- Que **reacciona** a la interacción: pulsar, escribir, marcar.
		- Que **llama a sus callbacks** con los datos correctos.
		- Los **estados condicionales**: error, deshabilitado, cargando, vacío.
	</TabItem>
	<TabItem label="No">
		- El estado interno (`useState`): no es visible para el usuario.
		- Clases CSS o estilos: eso lo verifica Storybook o Playwright.
		- Que React funciona (que `onClick` dispara al hacer clic).
		- Componentes sin lógica que solo pintan texto estático.
	</TabItem>
</Tabs>

## 🧩 Aplicación en el proyecto

En tu aplicación React, esta página se traduce en:

- Un test por **formulario**: datos válidos → callback llamado; datos inválidos → mensaje y callback no llamado.
- Un test por **lista**: con elementos, muestra cada uno; vacía, muestra el mensaje de "sin datos".
- Un test por **componente interactivo** (contador, filtro, selector): la interacción produce el cambio visible esperado.
- Si el componente carga datos con `fetch`, sustituye `fetch` con `vi.spyOn` (página anterior) y usa `findBy*` para esperar a que aparezcan.

Con eso, los componentes que concentran la lógica de la interfaz quedan cubiertos sin probar la implementación.

## Resumen rápido

| Paso | API |
| :--- | :--- |
| Configurar | `test: { environment: "jsdom", setupFiles }` + `import "@testing-library/jest-dom/vitest"` |
| Renderizar | `render(<C prop={x} />)` |
| Encontrar | `screen.getByRole("button", { name })`, `getByLabelText`, `getByText`; `container` solo para nodos sin rol ni texto |
| Variantes | `getBy` (debe estar) · `queryBy` (no debe) · `findBy` (aparecerá, con `await`) |
| Interactuar | `const user = userEvent.setup()` → `await user.click/type/clear` |
| Comprobar | `toBeInTheDocument`, `toBeDisabled`, `toHaveValue`, `toHaveTextContent`, `toBeChecked` |
| Callbacks | `vi.fn()` + `toHaveBeenCalledWith` |

## Convención práctica

<Steps>
	1. Busca por **rol y nombre accesible** antes que por texto, y por texto antes que por `data-testid`. Si no puedes encontrar algo por rol, suele ser señal de que al componente le falta una `<label>` o un rol.
	2. Un `userEvent.setup()` **por test**, y `await` en cada interacción.
	3. `queryBy` solo para afirmar ausencia; `getBy` para todo lo demás.
	4. Comprueba **comportamiento visible y callbacks**, nunca estado interno ni clases CSS.
	5. Si un test de componente necesita `fetch`, **móckealo**; un test de componente nunca espera a la red.
</Steps>
