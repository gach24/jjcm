### Del HTML al JSX

Ahora la página entera pasa a `App.tsx`. Es un componente demasiado grande, y en la página de componentes lo dividirás; de momento el objetivo es ver el contenido dentro de React.

<Steps>
	1. Abre `index.html` del material y copia **todo lo que hay dentro de `<body>`** (el `header`, el `main` y el `footer`, sin la etiqueta `body`).
	2. Pégalo en `App.tsx` dentro de un fragmento `<>…</>`:

		```tsx title="src/App.tsx"
		const App = () => {
			return (
				<>
					{/* aquí va el header, el main y el footer de la página */}
				</>
			);
		};

		export default App;
		```

	3. Las imágenes ahora se sirven desde `public/`, con ruta absoluta. Usa **Buscar y reemplazar** de VS Code (`Ctrl+H`) sobre `App.tsx` para cambiar `./img/` por `/img/`.
	4. Guarda: Prettier reformatea el archivo. Arranca `npm run dev` y comprueba que se ve todo el contenido: logotipo, botón del carrito, el `aside` del carrito con su tabla, el título "Nuestra Colección", las doce guitarras con su botón y el pie.
</Steps>

<Aside type="note" title="Por qué no hay errores de `class`">
	Como el HTML viene sin clases, no hay nada que convertir a `className`. Lo verás en cuanto escribas la primera clase de Tailwind en un componente: en JSX el atributo es `className`, porque `class` es palabra reservada de JavaScript. El resto de reglas de JSX (toda etiqueta se cierra, un único elemento raíz, atributos en camelCase) se explican en la página de componentes.
</Aside>

## Vitest y Testing Library

El proyecto se prueba desde hoy. La configuración es la de la [unidad de Vitest](/jjcm/di/units/testing/vitest/03-testing-react/#instalación-y-configuración); aquí se aplica sin explicarla de nuevo.

<Steps>
	1. Instala Vitest, jsdom y Testing Library:

		```bash
		npm install -D vitest jsdom @testing-library/react @testing-library/dom @testing-library/user-event @testing-library/jest-dom
		```

	2. Añade el bloque `test` a la configuración de Vite (la primera línea le dice a TypeScript que esa propiedad existe):

		```ts title="vite.config.ts" {1,9-12}
		/// <reference types="vitest/config" />
		import react from '@vitejs/plugin-react';
		import tailwindcss from '@tailwindcss/vite';
		import { defineConfig } from 'vite';

		// https://vite.dev/config/
		export default defineConfig({
			plugins: [tailwindcss(), react()],
			test: {
				environment: 'jsdom',
				setupFiles: './src/setupTests.ts',
			},
		});
		```

		```ts title="src/setupTests.ts"
		import '@testing-library/jest-dom/vitest';
		import { cleanup } from '@testing-library/react';
		import { afterEach } from 'vitest';

		afterEach(() => {
			cleanup();
		});
		```

		`setupFiles` indica un archivo que Vitest ejecuta **antes de cada archivo de test**, para preparar el entorno una sola vez en lugar de repetirlo en cada `.test.tsx`. Este hace dos cosas:

		- La primera línea registra en `expect` los **matchers de jest-dom**: `toBeInTheDocument()`, `toBeDisabled()`, `toHaveValue()`… Sin ella, `expect(elemento).toBeInTheDocument()` no existe y el test falla antes de empezar.
		- `afterEach(cleanup)` **desmonta** los componentes renderizados al terminar cada test. Testing Library lo haría sola si `afterEach` fuera una función global, pero en Vitest no lo es, así que hay que registrarlo. Sin esta línea, lo que renderiza un test sigue en el DOM durante el siguiente, y una consulta como `getByRole('heading')` fallaría con *Found multiple elements* en cuanto hubiera dos tests sobre el mismo componente.

	3. Añade el script `"test": "vitest"` a `package.json`.
	4. Escribe el primer test: la app muestra el título del catálogo.

		```tsx title="src/App.test.tsx"
		import { render, screen } from '@testing-library/react';
		import { describe, expect, it } from 'vitest';
		import App from './App';

		describe('App', () => {
			it('shows the collection title', () => {
				render(<App />);
				expect(
					screen.getByRole('heading', { name: 'Nuestra Colección' })
				).toBeInTheDocument();
			});
		});
		```

	5. Ejecútalo una vez y comprueba que pasa:

		```bash
		npx vitest run
		```

		```txt
		 ✓ src/App.test.tsx (1 test)

		 Test Files  1 passed (1)
		      Tests  1 passed (1)
		```
</Steps>

Es un test modesto, pero deja montada la infraestructura. Fíjate en que no depende de los estilos: cuando añadas Tailwind a los componentes, seguirá pasando. En cada página siguiente, cada componente nuevo llega con su archivo `.test.tsx` al lado.

## Storybook

Lo mismo con la documentación visual: Storybook se instala ahora y cada componente que crees tendrá su story. La [unidad de Storybook](/jjcm/di/units/documentation/storybook/01-introduction/) explica qué es y cómo escribir stories; aquí solo lo dejas funcionando.

<Steps>
	1. Instala Storybook con las funciones de documentación y accesibilidad, sin arrancarlo al terminar:

		```bash
		npx storybook@latest init --yes --no-dev --features docs a11y
		```

		El comando, parte por parte:

		| Parte | Qué hace |
		| :--- | :--- |
		| `npx storybook@latest` | Descarga y ejecuta la última versión del CLI de Storybook sin instalarla globalmente, igual que `npm create vite@latest` |
		| `init` | Añade Storybook a un proyecto que ya existe: detecta el framework (React) y el bundler (Vite) y elige el paquete adecuado, `@storybook/react-vite` |
		| `--yes` | Responde "sí" a todas las preguntas del asistente, para que el resultado sea el mismo en todos los equipos |
		| `--no-dev` | No arranca Storybook al terminar; lo harás tú después de configurarlo |
		| `--features docs a11y` | Instala solo dos extras: **docs** (documentación automática de cada componente) y **a11y** (panel que señala problemas de accesibilidad). Sin esta opción instalaría además la integración con Vitest, que no queremos |

		Al terminar, el asistente ha instalado los paquetes, ha creado `.storybook/` con `main.ts` y `preview.tsx`, ha añadido los scripts `storybook` y `build-storybook` a `package.json`, ha ampliado `.gitignore` y ha generado stories de ejemplo en `src/stories/`.

	2. Borra la carpeta `src/stories/`: son ejemplos que no pertenecen a GuitarLA.
	3. Sustituye `.storybook/preview.tsx` para cargar el CSS del proyecto (así las stories verán las clases de Tailwind que escribas en las páginas siguientes) y activar la documentación automática:

		```tsx title=".storybook/preview.tsx" {3,6}
		import type { Preview } from '@storybook/react-vite';

		import '../src/index.css';

		const preview: Preview = {
			tags: ['autodocs'],
			parameters: {
				controls: {
					matchers: {
						color: /(background|color)$/i,
						date: /Date$/i,
					},
				},
			},
		};

		export default preview;
		```

	4. El asistente instala `eslint-plugin-storybook`. Añádelo a `eslint.config.js` para que ESLint también revise las stories:

		```js title="eslint.config.js" ins={5,24}
		import js from '@eslint/js';
		import prettier from 'eslint-config-prettier';
		import reactHooks from 'eslint-plugin-react-hooks';
		import reactRefresh from 'eslint-plugin-react-refresh';
		import storybook from 'eslint-plugin-storybook';
		import { defineConfig, globalIgnores } from 'eslint/config';
		import globals from 'globals';
		import tseslint from 'typescript-eslint';

		export default defineConfig([
			globalIgnores(['dist', 'storybook-static']),
			{
				files: ['**/*.{ts,tsx}'],
				extends: [
					js.configs.recommended,
					tseslint.configs.recommended,
					reactHooks.configs.flat.recommended,
					reactRefresh.configs.vite,
					prettier,
				],
				languageOptions: {
					ecmaVersion: 2020,
					globals: globals.browser,
				},
			},
			...storybook.configs['flat/recommended'],
		]);
		```

	5. Incluye la carpeta `.storybook/` en la configuración de TypeScript. `tsconfig.app.json` solo cubre `src/`, así que VS Code trata `preview.tsx` como un archivo suelto, sin saber que el proyecto usa JSX ni dónde están los tipos, y lo llena de errores falsos:

		```json title="tsconfig.app.json" ins={2}
		{
			"include": ["src", ".storybook/**/*"]
		}
		```

		Con esto `tsc -b` también comprueba los tipos de `main.ts` y `preview.tsx` en cada `npm run build`.

	6. Escribe una primera story que muestre la app completa. `layout: 'fullscreen'` quita el relleno que Storybook añade alrededor, que aquí no tiene sentido:

		```tsx title="src/App.stories.tsx"
		import type { Meta, StoryObj } from '@storybook/react-vite';
		import App from './App';

		const meta = {
			component: App,
			parameters: {
				layout: 'fullscreen',
			},
		} satisfies Meta<typeof App>;

		export default meta;
		type Story = StoryObj<typeof meta>;

		export const Default: Story = {};
		```

	7. Arranca Storybook y comprueba en `http://localhost:6006` que la story **App / Default** muestra el contenido de la página y que la pestaña **Docs** existe. Páralo con `Ctrl+C`.

		```bash
		npm run storybook
		```
</Steps>

<Aside type="caution" title="No instales la opción `test` de Storybook">
	Si ejecutas `npx storybook@latest init` sin `--features`, el asistente instala además su integración con Vitest: descarga navegadores de Playwright, añade varios paquetes y **reescribe `vite.config.ts`** con una configuración por proyectos. Es útil en equipos grandes, pero complica el proyecto de aula y choca con la configuración de Vitest de esta página. Las pruebas de componentes se escriben con Testing Library, como en la unidad de pruebas.
</Aside>

## 🧩 Aplicación en el proyecto

Dos decisiones de esta página marcan cómo se trabaja en el resto de la unidad. La primera: **las herramientas de calidad se instalan antes de escribir el primer componente**, no cuando la aplicación ya está hecha; cada `Header`, `Guitar` o `Footer` llegará con su `.test.tsx` y su `.stories.tsx`. La segunda: **el marcado va antes que el estilo**. Partir de HTML semántico y añadir las utilidades de Tailwind al extraer cada componente te obliga a entender qué hace cada clase, en lugar de copiar un bloque de veinte que escribió otro.

## Convención práctica

<Steps>
	1. **Cuatro comandos antes de cada commit**: `lint`, `format:check`, `vitest run` y `build`.
	2. **Cada componente nuevo** llega con su `.test.tsx` y su `.stories.tsx` al lado, en el mismo commit.
	3. **Marcado primero, estilo después**: las clases de Tailwind se escriben al extraer cada componente, con la captura de `design/` delante.
	4. **Rutas de imágenes absolutas** (`/img/…`): lo que está en `public/` se sirve desde la raíz.
	5. **`storybook-static/` y `coverage/` no se versionan**; están en `.gitignore` y en `.prettierignore`.
</Steps>
